# Agent Note: 资产账户分层体系与次卡支持

Status: proposed

## Problem

当前系统在 `src/constants.ts` 中将 `accounts.type` 扁平地划分为 10 种类型（`cash`、`debit`、`credit`、`virtual`、`prepaid`、`investment`、`receivable`、`payable`、`loan`、`other`），虽然在内部以 `nature: 'asset' | 'liability'` 区分资产与负债，但从家庭日常记账的心智模型与预付消费场景出发存在两点明显缺口：

1. **账户分组不够直观**：用户习惯按三大核心账户组管理资产与负债——**资金账户**（现金、微信、支付宝、银行储蓄卡等日常流动资金）、**充值账户**（理发卡、饭店预存、物业/燃气预充等商家储值型预付卡）与**信用账户**（花呗、白条、信用卡等先消费后还款账户）。目前三类混在 10 个平铺选项中，且信用账户已建表的 `credit_limit`（额度）、`bill_day`（账单日）、`due_day`（还款日）尚未开放 UI 与统计逻辑。
2. **缺少按次计费的「次卡」支持**：家庭常见消费中有大量按次数而非按余额扣减的预付服务卡（例如 10 次洗车卡、20 次理发卡、健身私教课、游泳次卡等）。现有 `prepaid` 账户只能记录人民币余额，无法直接管理总次数、剩余次数、单次核销扣减、有效期到期提醒及购买成本向各次消费的摊销折算。

## Proposal

在进入正式实现前，将核心设计规划如下（具体实现边界需在实施前通过 `grill-me` 访谈与用户对齐确认）：

1. **三层账户视图分组（向后兼容现有 `accounts.type`）**
   - **资金账户**：聚合 `cash`、`debit`、`virtual`（支付宝/微信等）及 `investment`；
   - **充值账户**：对应 `prepaid` 余额储值卡及新增的次卡类型，支持独立卡片区展示剩余余额或剩余次数；
   - **信用账户**：聚合 `credit`（信用卡、花呗、白条）及 `payable` / `loan`，开放 `credit_limit`、`bill_day`、`due_day` 配置与可用额度/待还金额计算。
2. **次卡（Session Card）能力设计**
   - 支持购卡时一次性录入总金额、总次数（自动或手动计算单次均摊金额）、有效期及关联支出账户；
   - 支持日常「核销记次」（剩余次数 `-1`），可选是否在消费统计/报表中按单次摊销金额计入对应分类支出，或在购卡时一次性计入支出而核销仅作次数台账；
   - 支持次卡剩余次数不足或临近过期时通过每 4 小时 Cron 写入 `notifications` 提醒。

### 待对齐的开放问题（待 `grill-me` 确认）

- 现有 10 种 `ACCOUNT_TYPES` 是保留底层 key 仅在前端做三大分组展示与筛选，还是新增专用类型 key（如 `session_card`）并做默认账户预设调整？
- 次卡购买与核销的财务记账口径：采用「购卡记资产转移（资金账户 → 充值账户），每次核销按单次成本计支出」还是「购卡即记支出，核销仅扣减次数台账」？
- 次卡与充值账户余额数据放在扩展的 `accounts` 表（或轻量扩展列）还是独立 `session_cards` 表？
- 信用账户是否需要自动生成账单日/还款日提醒及「信用卡还款」快捷转账入口？

## Alternatives considered

- **在 `accounts` 表直接新增次卡列（`total_sessions` / `remaining_sessions` / `expires_at` 等）**：复用现有账户列表、净资产汇总、OpenAPI `/api/open/accounts` 和权限体系，开发改动小，但充值型金额账户与按次核销账户在交易语义（金额 vs 次数）上差异较大，强行共用 `balance_cents` 和 `transactions.amount_cents` 容易导致净资产与流水汇总口径混淆。
- **新增独立 `session_cards` 及核销流水表（或通过 `transactions` 关联 `card_id`）**：领域模型清晰，可将「剩余次数」与「人民币余额/净资产」彻底解耦，同时把次卡与充值账户并列展示在资产页面；代价是需要新增 SQL Migration、独立增删改查路由及对应 OpenAPI 端点。
- **继续沿用现有 `prepaid` 账户手动折算**：零开发成本，但每次使用次卡都必须用户手动换算单次价格并作为普通金额支出录入，无法回答「卡里还剩几次、何时过期」，不能满足用户诉求。

## Acceptance criteria

- 经过 `grill-me` 访谈达成设计共识，并形成细化实现方案后推进编码：
  - `/accounts` 页面清晰划分资金账户、充值账户、信用账户（含花呗/白条/信用卡）并支持关键属性编辑；
  - 次卡支持开卡、核销（扣减次数）、查看剩余次数/有效期与过期提醒；
  - 所有变更符合 [homeledger-worker-architecture](../../implemented/architecture/2026-11-23-homeledger-worker-architecture.md) 中的 D1 低读写与零冗余表红线。

## Risks

- 若在次卡与普通账户之间引入复杂的实时重算或高频统计表，可能增加 D1 读写开销，需坚持单次 `db.batch()` 原子扣减原则。
- 账务口径（购卡即支出 vs 核销摊销支出）若未提前与用户拍板，将直接影响月度支出报表与预算统计预期，因此必须先经过 `grill-me` 访谈再实施。
